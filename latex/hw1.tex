\Question{CISC, RISC, Accumulator, and Stack: Comparing ISAs}

\lstset{language=c}
\begin{lstlisting}
unsigned int rotate(unsigned int x, unsigned int n) {
    unsigned int msb;

    while (n != 0) {
        msb = x >> 31;
        x = (x << 1) | msb;
        n--;
    }
    return x;
}
\end{lstlisting}

\begin{Parts}
	\Part \textbf{CISC} \\
     In total there are 15 bytes in the program. There needs to be 79 bytes of instructions needed to be fetched. We have to be aware that the loop condition is fetched $n + 1$ iterations, so the total number bytes fetched is $(6 * 4) + (5 * 11) = 79$ by accounting the number of iterations in the loop condition and loop body. In the program, there is no memory stored or loaded, at least in the program given. Thus 0 bytes of data loaded or stored. \\
\lstset{language=[RISC-V]{Assembler}}
\begin{lstlisting}

       jz done
       mov %eax,%ebx 
       shr $31,%ebx 
       shl $1,%eax 
       or %ebx,%eax d
       ec %ecx
       jmp loop 
done:  ...
\end{lstlisting}
	\Part \textbf{RISC} \\
    Here lies the translation from x86 to RISC-V assembly \\
\lstset{language=[RISC-V]{Assembler}}
\begin{lstlisting}
loop:  beq a0, x0, done
       mv t0, a1
       srli t0, t0, 31
       slli a1, a1, 1
       or a1, t0, a1
       addi a0, a0, -1
       j loop
done:  ...
\end{lstlisting}
	The instruction set between 32 bit and 64 bit ISA should remain the same bit width, so all we would need to do is multiply how many instructions are in the converted assembly code by 4 bytes. Thus, there is 1 instruction for the branch condition and 6 instruction for the loop body. $(6 * 4) + (5 * 24) = 144$ bytes of instructions fetched. Again, there is no loading or storing, so 0 bytes of memory is accessed/transferred. 
	
	\Part \textbf{Stack} \\
    Here lies the translation from x86 to stack assembly: \\
\lstset{language=[RISC-V]{Assembler}}
\begin{lstlisting}
       pop 0x8000
loop:  push 0x8000
       beqz done
       pop 0x8004
       push 0x8004
       sign
       push 0x8004
       shl
       or
       push 0x8000
       dec
	   jump loop
done:  ...
\end{lstlisting}

Push, pop, and branch instructions are the most expensive and take 3 bytes. Other instructions are 1 byte. The program itself has $(7 * 3) + (4 * 1) = 25$ bytes. The number of bytes that needs to be fetched is 119 bytes. The number of bytes loaded depends on the number of pushes, so there are $(4 * 6) + (4 * 3 * 5) = 84$ bytes loaded from memory. The number of bytes stored depends on the number of pops, so there are  $4 + (4 * 5) = 24$ bytes stored to memory.

Interestingly enough, for the stack machine, since we are limited to only two registers, there is register spilling over to memory. I've desined the code in such a way that does not use more than two stack registers at a time, so the number of bytes loaded and stored will actually remain the same if it was expanded to 8. But if my program did use more stack registers than it has allocated, the number of bytes stored and loaded would decrease.
    \Part \textbf{Accumulator} \\
    Here lies the translation from x86 to accumulator assembly: \\
    \lstset{language=[RISC-V]{Assembler}}
    \begin{lstlisting}
    loop:  load 0x8004
           beqz done
           dec
           store 0x8004
           load 0x8000
           shl
           swap
           load 0x8000
           sign
           store 0x8000
           swap
           or 0x8000
    done:  load 0x8000
    \end{lstlisting}

There are 29 bytes of instructions in the program. The number of bytes that needs to be fetched is $(6 * 6) + (5 * 20) + 3 = 139$ bytes. The number of bytes loaded is $(6 * 3) + (6 * 5) = 48$ bytes. The number of bytes stored is $(6 * 3) + (6 * 6) = 56$ bytes.

    \Part \textbf{Conclusions} \\
    We notice that RISC-V has to fetch a lot of instructions, and they are relatively low for CISC, stack, and accumulator ISAs. We also notice that stack and accumulator ISAs using memory for a simple program, while CISC and RISC maintiain their data in registers. Also, the stack and accumulator ISAs spill registers when too much data is being moved around which is why the number of bytes loaded and stored is larger. When choosing an ISA, I would choose RISC as the instruction set is very simple and not much data is being moved around, causing me the programmer to develop more easily. There was extra thought involved for stack and accumulator as I needed to figure out how to handle memory.

\Question{6-Stage Pipeline}
\begin{Parts}
    \Part \textbf{Hazards: Second Write Port} \\
    	The second write port allows arithmetic operations to write back faster by detecting RAW hazards earlier and avoiding them as well. The is enough gap between instructions where a RAW like the following RISC-V assembly would not be a problem with the second write port.
	\lstset{language=[RISC-V]{Assembler}}
    \begin{lstlisting}
    add x1, x1, x1
    add x2, x2, x2
    add x3, x1, x3
    \end{lstlisting}
    \Part \textbf{Hazards: Bypasses Removed and New Hazards} \\
    	ALU results don't have to be bypassed from end of M2 and writeback stage. The bypasses from the end of M1 to end of Instruction Decode can also be removed, as well as the end of M1 to the end of Instruction Fetch. Because of the earlier writeback, there is a new WAW hazard when you handle non ALU writebacks, which happen later in the pipeline. The writeback needs to be scheduled or stalled in order to let two concurrent writebacks from the ALU and writeback mux not have a data race.
    \Part \textbf{Precise Exceptions} \\
		We know that the datapath detects a misaligned address in the beginning of M2. Since a write back from ALU happens much earlier, we might not be able to detect an exception synchronously. Below, we notice that an incorrect 
	\verb|lw| happens, but the \verb|addi| instruction will execute before catching the exception. 
	\lstset{language=[RISC-V]{Assembler}}
    \begin{lstlisting}
	lw x1, -3(x1)
	addi x2, x0, 0xBEEF
    \end{lstlisting}
    \Part \textbf{Precise Exceptions: Implemented using a Interlock} \\
		Precise exception can be implemented by adding a new interlock that will stall an instruction. Particularly in our 6-stage pipeline, we stall any instruction that uses the ALU in the ID stage, but uses an instruction pipelined in the EX stage that is a memory operation. This is so that we let the memory operation finish first in the pipeline, then let the ALU operation finish due to the earlier writeback. Thus, the snipped below, which is the same as before, is a good example:
	\lstset{language=[RISC-V]{Assembler}}
    \begin{lstlisting}
	lw x1, -3(x1)
	addi x2, x0, 0xBEEF
    \end{lstlisting}
    \Part \textbf{Precise Exceptions: Implemented using an Extra Read Port} \\
    	We can implement precise exceptions by levering the extra read port to bubble or forward the older value of a register to be updated to a pipelined register. This is so we avoid WAW hazards with a ALU operations happening right after a load or store. This effectively removes the need for interlocking as there are no data hazards as we explored with previous questions. 
\end{Parts}

\Question{Iron Law of Processor Performance}

\begin{Parts}
	\Part \textbf{Adding a branch delay slot}
		\begin{enumerate}[i]
			\item \textbf{Instructions / Program} \\
				Increase, NOPs fill in the missing delay.
			\item \textbf{Cycles / Instruction} \\
				Decrease, control hazards are eliminated since NOPs are executed. This is especially true in a RISC ISA.
			\item \textbf{Seconds / Cycles} \\
				No effect, should remain the same as there is nothing else going on.
			\item \textbf{Overall Performance} \\
				Ambiguous, this is subjective to what kinds of program the CPU is going to run. If it has a lot of branch instructions, then it will be beneficial if it can fill in the delay slots with other instructions.
		\end{enumerate}
	\Part \textbf{Adding a complex instruction}
		\begin{enumerate}[i]
			\item \textbf{Instructions / Program} \\
				Decrease, as a CISC instruction could potentially replace a bunch of RISC instructions in a single microcoded subroutine.
			\item \textbf{Cycles / Instruction} \\
				Increase, there are now more cycles to execute a complex instruction, such as a separate stage for a microcoded instruction/subroutine.
			\item \textbf{Seconds / Cycles} \\
				Increase, more control logic will increase the critical path and the time it takes to complete a cycle.
			\item \textbf{Overall Performance} \\
				Ambiguous, as it's often dependent how well the programmer can utilize the instruction. For CISC, compilation may be easier to optimize, while it's the opposite for RISC.
		\end{enumerate}
	\Part \textbf{Reduce number of registers in the ISA}
		\begin{enumerate}[i]
			\item \textbf{Instructions / Program} \\
				Increase, there will be more loads/stores since the registers need to spill into memory.
			\item \textbf{Cycles / Instruction} \\
				Increase, since there are more loads and stores, this could also lead to more stalls when fetching from memory.
			\item \textbf{Seconds / Cycles} \\
				No effect, given that all registers perform the same.
			\item \textbf{Overall Performance} \\
				Ambiguous, there is a tradeoff. Depending on the program, RISC-V could not utilize all it's registers.
		\end{enumerate}
	\Part \textbf{Improving memory access speed}
		\begin{enumerate}[i]
			\item \textbf{Instructions / Program} \\
				No effect, instructions don't care about how fast memory is.
			\item \textbf{Cycles / Instruction} \\
				Decrease, there could be less stalls, thus less cycles per instruction.
			\item \textbf{Seconds / Cycles} \\
				Decrease, memory access speed is improved, thus less seconds it takes per cycle for memory fetch.
			\item \textbf{Overall Performance} \\
				Improve, memory is the main bottleneck on the CPU, and there has historically been a gap between memory and CPU performance. Improving memory latency to match up with the transistors and logic gates of the CPU will help performance.
		\end{enumerate}
	\Part \textbf{Adding 16-bit versions of the most common instructions in RISC-V (normally 32 bits in length) to the ISA (i.e., make RISC-V a variable-length ISA)}
		\begin{enumerate}[i]
			\item \textbf{Instructions / Program} \\
				No effect, the number of instructions stay the same.
			\item \textbf{Cycles / Instruction} \\
				Decrease, there will smaller instructions to fetch, and cycles can decrease since memory latency can be improved. This is if all the instructions fetched fit in the instruction cache.
			\item \textbf{Seconds / Cycles} \\
				Increase, instruction decode may become more complicated. Also, since these instructions could be packed tightly with variable length instruction length, there may be extra time to account for instruction memory alignment. 
			\item \textbf{Overall Performance} \\
				No effect, the tradeoff between less cycles per instruction and more seconds per cycle cancel each other out. 
		\end{enumerate}
	\Part \textbf{For a given CISC ISA, changing the implementation of the micro-architecture from a microcoded engine to a RISC pipeline (with a CISC-to-RISC decoder on the frontend)}
		\begin{enumerate}[i]
			\item \textbf{Instructions / Program} \\
				No effect, the instructions are still fed the same way from software, it's only the hardware being changed.
			\item \textbf{Cycles / Instruction} \\
				Decrease, microcode takes more cycles to execute per instruction, but since it's running on a RISC pipeline it'll decrease it to 1 cycles per instruction. 
			\item \textbf{Seconds / Cycles} \\
				No effect, assuming that microcode cycles and RISC cycles in the pipeline are the same. 
			\item \textbf{Overall Performance} \\
				Improve, the decrease of CPI from CISC to RISC is a drastic improvement for CPI.
		\end{enumerate}
\end{Parts}
