\section*{(Open-ended) Problem 4.1: Designing Your Own Branch Predictor}
My partner for this lab was Kevin Chang. This copy of the lab is the main copy, please use this to grade. \\ \\
We first of began by reading how to combine multiple branch predictors from McFarling. \cite{McFarling1993CombiningBP} But after beginning development, we realized that it took too long to try to implement a global and local predictor combined with a arbiter predictor. To debug and simulate all of these would take a lot of time. To save on time and have our code be simplistic, we stuck with just optimizing the local predictor. We read the Alpha 21264 microprocessor's branch prediction implementation and followed the design patterns of its local predictor. \cite{755465} We realized that the starter code doesn't utilize the history of the branches, so we used \verb|hist| to our advantage and some bitwise manipulation to access and predict a value if the branch will be taken or not, as well as using 10-bit branch patterns indexed by PC, which is then used to index a set of 3-bit counters as mentioned in the Alpha microprocessor branch prediction design. \cite{755465} But we later found out through tuning that looking at the past 4 branch patterns was optimal, at least for the Dhyrstone benchmark. Increasing it more gave diminishing returns. 


We calculated the amount of state that our branch predictor has via print statements and trying to estimate and detect patterns. But, in the end we used the default 1024 that Kessler's design suggests. \cite{755465}. We found that increasing or decreasing the state has negligible effect when decreased to 512 or 2048, meaning that maybe the benchmarks do not stress the branch predictor state as much and it could be smaller. Having the state larger and implementing it in hardware would only add more complexity and latency. In a software branch predictor, it could lead to more CPI and higher algorithmic runtime complexity. Other parameters that we found that affected the accuracy was the number of history entries to look at, which is explained later below. 

In the next page lies the source code of our branch prediction in \verb|predictor_sw.cc|.
\newpage
\lstset{language=c}
\begin{lstlisting}
#define BIMODAL_TABLE_SIZE 1024
#define BIMODAL_HISTORY_BITS 4
#define MAX_COUNTER 3

#include <stdint.h>
#include <stdio.h>

int bimodal_table[BIMODAL_TABLE_SIZE];

extern "C" void initialize_branch_predictor() {
    for (int i = 0; i < BIMODAL_TABLE_SIZE; i++)
        bimodal_table[i] = 0;
}

extern "C" void predict_branch(unsigned long long ip, unsigned long long hist, unsigned char *pred)
{
    uint32_t hash = ip % BIMODAL_TABLE_SIZE & 31;
    uint32_t update = hash >> BIMODAL_HISTORY_BITS;
    update = ((update ^ hist) % 32) << BIMODAL_HISTORY_BITS;
    hash = ((hash & 31) | update) % BIMODAL_TABLE_SIZE;

    *pred = (bimodal_table[hash] >= ((MAX_COUNTER + 1)/2)) ? 1 : 0;
}

extern "C" void update_branch(unsigned long long ip, unsigned long long hist, unsigned char taken){
    uint32_t hash = ip % BIMODAL_TABLE_SIZE;
    uint32_t update = hash >> BIMODAL_HISTORY_BITS;
    update = ((update ^ hist) % 32) << BIMODAL_HISTORY_BITS;
    hash = ((hash & 31) | update) % BIMODAL_TABLE_SIZE;

    if (taken && (bimodal_table[hash] < MAX_COUNTER))
        bimodal_table[hash]++;
    else if ((taken == 0) && (bimodal_table[hash] > 0))
        bimodal_table[hash]--;
}
\end{lstlisting}
\newpage

Considering that this is relatively terse, this is best we think we could do given the amount of time we wanted to spend. Adding too much algorithmic complexity could lead to higher CPI/lower IPC. To save on time, we only benchmarked on Dhrystone when debugging performance, but later on realized that optimizing over one benchmark does not necessarily transfer to other benchmarks due to the nature of the code and instruction stream. For example, we will see an even worse performance on quicksort benchmark, and there is really nothing that can be done about that since sorting takes unpredictable branch patterns due to the nature of the random input. Because Dhrystone seems to be a static benchmark (data doesn't change between runs), we think that is the reason why our branch prediction shows the best improvement. There is only slight improvements over mathematically intense benchmarks such as multiply, median, and sparse matrix-vector multiply. If given more time, we would've went beyond and implemented the global and arbiter predictors. Our branch predictor could potentially perform better on repetitive instruction streams such as Dhrystone. But it would perform poorly on random branches such as sorting. We are not sure why vvadd performs worse than the base configuration and think it's minor as the difference is minimal.
