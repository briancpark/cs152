\subsection*{3.3 Matrix Transposition Case Study}
\begin{Parts}
	\Part How many cycles does the transpose operation take? \\
		The transpose operation takes 1350476 cycles.
	\Part What is the miss rate of the L1 data cache? \\
		The miss rate of the L1 data cache is $\frac{18661}{16384 + 16407}$. The total number of memory accesses is found by counting the number of loads and stores. Therefore, the miss rate is 56.9\%.
	\Part Why does the naive transpose code result in non-ideal cache performance? \\
		The code has to transfer data diagonally through the matrix. If the matrix being transposed is fairly large, then a large stride access can hurt cache hits and memory performance. Note that it's really doing a transformation from row major to column major order, so cache performance will definitely take a hit.
	\Part Which memory access in the code incurs the most misses, and why? \\
		Obviously, this line of code: \verb|dst[j][i] = src[i][j]| incurs the most misses. Specifically, writing to \verb|dst[j][i]| will incur the most since the CPU will have already loaded \verb|src[i][j]| to a register from memory, but when it wants to write to \verb|dst[j][i]|, it will most likely miss the cache and stall for a memory fetch. Also note that \verb|dst| will be accessed in column major order when the matrix is stored as row major.
\end{Parts}

\subsection*{3.4 Cache Blocking}
\lstset{language=c}
\begin{lstlisting}
#define min(a, b) (((a) < (b)) ? (a) : (b))

void __attribute__ ((noinline)) transpose(mat_nxm_t dst, const mat_mxn_t src)
{
    register size_t i, j, l, k;
    register size_t blocksize = 8;
    
    for (i = 0; i < MAT_M; i += blocksize) {
        for (j = 0; j < MAT_N; j += blocksize) {    
            for (l = j; l < min(j + blocksize, MAT_N); ++l) {
                for (k = i; k < min(i + blocksize, MAT_M); ++k) {
                    dst[l][k] = src[k][l];
                }
            }
        }
    }
}
\end{lstlisting}

\begin{Parts}
	\Part For the given matrix dimensions, what is the optimal blocking factor B? \\
	The optimal blocking is $8\times8$. Also, some loop ordering needed to be swapped in order for this to be cache optimal.
	\Part What is the performance improvement using cache blocking over the naive code? \\
	This achieves a miss rate of 21.21\%, which is an improvement over naive code by 2.68 times.
	\Part It turns out that the block size B×B which yields the lowest miss rate is much smaller than what one might expect based solely on the 4 KiB capacity of the L1 data cache. What is the reason for this? (Hint: Consider the access pattern within a block, particularly how the rows of the rectangular matrices map to cache sets and which type of cache misses dominate for larger B.) \\
	Considering that the L1 cache is 4KiB, this can hold 1024 32 bit integers. Since the matrix to be transposed will be accessed in column major, this will incur much more cache misses. That is why the block size is much smaller.
\end{Parts}

\subsection*{3.6 Multi-level Caches}
\lstset{language=c}
\begin{lstlisting}
#define min(a, b) (((a) < (b)) ? (a) : (b))

void __attribute__ ((noinline)) transpose(mat_nxm_t dst, const mat_mxn_t src)
{
    register size_t i, j, l1, k1, l2, k2;
    register size_t l1_blocksize = 8;
    register size_t l2_blocksize = 64;
    
    for (i = 0; i < MAT_M; i += l2_blocksize) {
        for (j = 0; j < MAT_N; j += l2_blocksize) {
            for (l1 = j; l1 < j + l2_blocksize; l1 += l1_blocksize) {
                for (k1 = i; k1 < i + l2_blocksize; k1 += l1_blocksize) {
                    for (l2 = l1; l2 < min(l1 + l1_blocksize, MAT_N); l2++) {
                        for (k2 = k1; k2 < min(k1 + l1_blocksize, MAT_M); k2++) {
                            dst[l2][k2] = src[k2][l2];
                        }
                    }
                }
            }
        }
    }
}
\end{lstlisting}

\begin{Parts}
	\Part Does adding another level of cache blocking improve performance compared to your previous code from 3.5? Why or why not? (\textbf{Hint}: Consider whether there is any locality left for the L2 cache to exploit.) \\
	Adding another level of cache blocking didn't improve performance compared to just L1 cache blocking, just stayed nearly the same. Using the same L1 block size of $8\times8$ and using $64\times64$ as the L2 kernel size, this gave us a miss rate of 21.23\%. This is probably due to no locality being left over. But what did improve was the number of cycles, as traversing the memory hierarchy induces less cycles or fetches to main memory, reducing the AMAT overall. It went from 527174 cycles to 432253 cycles.
\end{Parts}

We believe the L1 Data Cache is 16kB. We noticed that 4, 8, and 16kB arrays all shared approximately the same cycles per iteration, with a sharp increase after 16kB. In order for this to be the case, their cache hit rates should be almost exactly the same, which is only possible if the cache is large enough to fully fit all 3 arrays. When pointer chasing first starts, random portions of the array are drawn in as cache lines. However, as the entire array is pulled in, every pointer chase after that is extremely fast. \bigbreak

We believe L1 Data Cache has a latency of 3 cycles. The average cycles per iteration is four cycles for 4-16kB. Given the large number of iterations, the average cycle count should be very close to the actual cycle count for a cached read, because once the cache is filled, the large number of fast cached reads rapidly outweighs the number of slow memory reads. We presume writing $idx$ takes 1 cycle,  so the remaining 3 cycles must be spent in the pointer chase. We assume that array bounds checking and index incrementing are not included as part of an iteration's time-to-execute (if so, then L1 latency is 1 cycle). \bigbreak


Our L2 cache size we found to be 64KB, with similar reasoning as L1 cache size. The relatively minor change in cycles per iteration implies very similar overall memory access times between the 16kB and 64kB data points, which can only be achieved if approximately the same percentage of the arrays reside in caches. This would have to be 100\% or close to 100\%. \bigbreak

We found L2 cache latency to be 36 cycles. The array of size 8192 has almost exactly a 5x worse cycles per iteration ($21$ versus $4.2$) than the array of size 4096. We presume that on average for every L1 cache hit in the size 4096 array, there is one cache miss that goes to L2 because the pointer chase is randomly distributed. Then, we can setup a multi-level AMAT equation. We assume the L2 miss rate is negligible on average because once the entire array is pulled in, cache hits will vastly outnumber cache misses. 
\begin{gather*}
        AMAT = L1HT+L1MR(L2HR +L2MR*L2MP) \\
    21 = 3 + .5(L2HT + 0*L2MP) \\
    36 = L2HT
\end{gather*}

Finally, we found DRAM latency to be 58 cycles. We setup another AMAT to solve for the L2 miss penalty. Similar to solving the L2HT, we found an array that was 8 times larger than what we determined was the L2 cache size. With randomly distributed indices, this should result in an L2 miss rate of 7/8. We plugged this into L2MR variable and solved for L2MP. We were skeptical of this result as it seemed far too low for main memory latency, but were unable to create another test that could measure DRAM latency. \bigbreak

We found our L1 I\$ line size to be 64B in size. We deduced this by running a sequence of \texttt{addi} instructions and noticed that every 15-16 instructions, there would be a jump of around 50 cycles in total cycle count. We believe this to be the code reaching the end of cached instructions and needing to pull in a new line of instructions from lower in the memory hierarchy. Thus,  $16 \times 4 = 64$ bytes as each instruction is 4 bytes. \bigbreak

We believe L1 I\$ replacement is LRU. We were also lucky to find that the L1 I\$ is 4-way set associative. This is done by writing code that holds 4 sets. We saturated the cache 4 times and made the 5th iteration of accesses read from one of the 4 sets we saturated. This did not incur any drastic difference in cycles (we used 50 cycles as a indicator and used jump instructions to branch to start of the iteration. This means that the cache size is $4 \times 64$ bytes or 256 bytes in total.

In fact, any more saturation of the cache caused the instruction cache to be replaced with LRU replacement policy. Looking at the Rocket chip source code, we realized there is either random replacement or LRU replacement policies available. We deduced that the replacement policy is LRU by saturating the cache 5 times where the LRU would evict the first entry of the cache. When we want to access the first entry again, it will not be resident inside the cache, thus incurring more cycles when it needs to be fetched from lower levels of memory. We found our L1 data cache lines to each be 64 bytes long. We determined this with the code below (cycle counting code has been omitted), a simply array copy. We noticed that every 16 elements copied, the cycle count would jump up by 40-100 cycles for one iteration. We determined this was a cache line of array elements being exhausted, requiring the processor to pull in a new line from a lower level.

L1 D associativity is LRU, we believe. We ran a program to saturate our data cache cache with an array larger than L1 D\$. Then, we stepped back through the array and measured the time to access elements. We found that the elements closest to the end were all fairly fast accesses. As we approached the middle of our array, we noticed an occasional jump in the cycle count, which is a new chunk of the array being pulled into memory. We know from RocketChip's config that eviction can be only LRU, psuedo-LRU or random, and we deduced it was LRU because out of all possible blocks that could be evicted, it was always the one that we had accessed least recently.
